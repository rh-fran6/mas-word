# Existing Cluster Workflow

## Status

`MANUAL_FALLBACK_SKILL_UNAVAILABLE` -- The `/agnosticv:catalog-builder` skill
does not natively support the existing-cluster integration model. This
document describes the gap and the selected integration approach.

## The gap

Standard RHDP AgnosticV catalog items provision infrastructure (OpenShift
clusters, VMs, cloud resources) as part of the order lifecycle. The
provisioning and deprovisioning are managed end-to-end by AgnosticD.

MAS World 2026 clusters are **provisioned externally** -- they exist before
any AgnosticV catalog item is ordered. The catalog items define only
**post-provisioning workloads** that configure these existing clusters.

This creates a gap in the standard AgnosticV model:

| Standard model | MAS World 2026 model |
|---|---|
| AgnosticV provisions the cluster | Cluster already exists |
| AgnosticD manages the full lifecycle | AgnosticD manages post-provision only |
| Cluster credentials are generated | Cluster credentials are pre-existing |
| Teardown deletes the cluster | Teardown removes workloads, not the cluster |
| One order = one cluster provisioned | One order = one existing cluster configured |

## Selected integration approach

### Option A: RHDP existing-cluster pool (preferred)

If RHDP supports registering pre-provisioned clusters in a pool:

1. Pre-provisioned clusters are registered with RHDP as pool members.
2. When a catalog item is ordered, RHDP assigns a cluster from the pool.
3. AgnosticD runs post-provision workloads against the assigned cluster.
4. On deprovision, AgnosticD runs teardown workloads but does not delete
   the cluster.
5. The cluster returns to the pool for potential reuse or external
   deletion.

This approach requires RHDP platform team support to configure the
existing-cluster pool.

### Option B: External orchestration with RHDP API

If RHDP does not support existing-cluster pools natively:

1. The fleet orchestration CLI (`mas-world-2026-automation/cli/`) manages
   cluster assignment independently.
2. The CLI invokes AgnosticD workloads directly against each cluster.
3. RHDP is used only for the Showroom interface, or not at all.
4. Access data is generated by the CLI and distributed through the
   operations tooling.

This approach is more operationally complex but removes the RHDP
dependency for cluster assignment.

### Option C: Hybrid model

1. RHDP manages the Showroom deployment and user-facing catalog.
2. The fleet orchestration CLI manages cluster preparation and assignment.
3. The CLI registers prepared clusters with RHDP for Showroom access.
4. Both systems share the same variable definitions (this catalog).

This is the most likely production approach.

## Required platform team work

Regardless of the selected option, the following work items require
coordination with the RHDP platform team:

### For Option A

1. Confirm that RHDP supports existing-cluster pools.
2. Define the cluster registration process and required metadata.
3. Define the credential handoff mechanism (kubeconfig, token, or
   username/password via secret reference).
4. Confirm the variable injection model for per-cluster parameters.
5. Confirm the teardown behavior (workload-only, not cluster deletion).
6. Confirm support for the 240-minute workload execution timeout.

### For Options B and C

1. Confirm the AgnosticD API or CLI invocation mechanism.
2. Confirm how access data is registered with RHDP for Showroom.
3. Confirm the Showroom deployment model for externally managed clusters.
4. Define the boundary between fleet CLI and RHDP responsibilities.

## Cluster inventory registration

Each cluster must be registered with the system that assigns it:

```yaml
# Example cluster registration (for external orchestration)
cluster:
  id: seat-01
  api_url: https://api.seat-01.example.com:6443
  admin_secret_ref: "secret://mas-world/clusters/seat-01/admin-kubeconfig"
  purpose: attendee
  seat_number: 1
  status: available
  platform:
    provider: aws
    region: us-east-2
```

For RHDP pool registration, the equivalent metadata must be provided in
whatever format the platform team requires.

## Credential model for existing clusters

Pre-provisioned clusters have their own administrative credentials. The
catalog does not generate these -- it consumes them via secret references.

```text
Credential lifecycle for existing clusters:

1. External provisioner creates the cluster and admin credentials.
2. Admin credentials are stored in the secret provider.
3. The secret reference is recorded in the cluster inventory.
4. AgnosticD resolves the secret reference at runtime.
5. Automation uses the credentials for cluster configuration.
6. Credentials are discarded from memory after use.
7. On teardown, admin credentials remain -- they belong to the cluster,
   not the event workload.
```

## Boundary between AgnosticV and external provisioning

```text
External provisioner:
  - Provision OpenShift clusters
  - Configure networking, DNS, ingress
  - Create admin credentials
  - Store credentials in secret provider
  - Register clusters with RHDP pool (Option A) or fleet inventory (B/C)
  - Delete clusters after the event

AgnosticV / AgnosticD:
  - Define catalog items and variable schemas
  - Define post-provision workload roles
  - Execute workloads against existing clusters
  - Return access data to RHDP
  - Execute teardown workloads on deprovision
  - Do NOT provision or delete clusters
```

## Open questions

1. Does RHDP support existing-cluster pools? If so, what is the
   registration API or process?
2. What metadata does RHDP require for each pool member?
3. Can RHDP pass per-cluster parameters (API URL, admin secret ref)
   to AgnosticD at order time?
4. What is the maximum workload execution timeout supported by RHDP?
5. Can RHDP's teardown hook be configured to skip cluster deletion?

These questions must be resolved with the RHDP platform team before
the rehearsal environment can use Option A.
