= Observability and Logging
:navtitle: Observability and Logging
:duration: 45 minutes

Install and configure the OpenShift Logging stack with Loki to observe your Maximo environment.

== Introduction

In this exercise you will install and configure a complete cluster logging stack from scratch using the OpenShift web console. By the end, you will have:

* Installed three operators (Logging, Loki, Cluster Observability)
* Created an S3-backed LokiStack for log storage
* Configured log collection and forwarding
* Enabled console-integrated log viewing
* Generated test logs and queried them with LogQL

== Architecture Overview

You will build the following stack:

[cols="1,2"]
|===
| Component | Purpose

| OpenShift Logging Operator
| Manages the log collection pipeline (Vector-based collector)

| Loki Operator
| Manages the LokiStack deployment for log storage and indexing

| Cluster Observability Operator (COO)
| Provides UIPlugin for integrated log viewing in the OpenShift Console

| LokiStack
| Stores and indexes logs with S3 backend

| ClusterLogForwarder
| Routes application, infrastructure, and audit logs to LokiStack

| AWS S3
| Object storage for Loki log data (pre-created for you)
|===

== Step 1: Install the OpenShift Logging Operator

. In the OpenShift web console, navigate to *Operators > OperatorHub*.
. In the search field, type `Red Hat OpenShift Logging`.
. Click the *Red Hat OpenShift Logging* tile.
. Click *Install*.
. On the Install Operator page, configure the following:
+
[cols="1,2"]
|===
| Setting | Value

| Update channel
| `stable-6.6`

| Installation mode
| A specific namespace on the cluster

| Installed Namespace
| `openshift-logging` (select *Create Namespace* if it does not exist)

| Update approval
| Automatic
|===
+
. Click *Install*.
. Wait for the status to show *Succeeded* on the Installed Operators page. This may take 1-2 minutes.

== Step 2: Install the Loki Operator

. Navigate to *Operators > OperatorHub*.
. In the search field, type `Loki Operator`.
. Click the *Loki Operator* tile (the one provided by Red Hat).
. Click *Install*.
. On the Install Operator page, configure the following:
+
[cols="1,2"]
|===
| Setting | Value

| Update channel
| `stable-6.6`

| Installation mode
| A specific namespace on the cluster

| Installed Namespace
| `openshift-logging`

| Update approval
| Automatic
|===
+
. Click *Install*.
. Wait for the status to show *Succeeded*.
. Navigate to *Operators > Installed Operators* and select the *openshift-logging* project from the namespace dropdown. Confirm that both *Red Hat OpenShift Logging* and *Loki Operator* show a status of *Succeeded*.

== Step 3: Install the Cluster Observability Operator

The Cluster Observability Operator (COO) enables integrated log viewing directly in the OpenShift Console.

. Navigate to *Operators > OperatorHub*.
. In the search field, type `Cluster Observability Operator`.
. Click the *Cluster Observability Operator* tile.
. Click *Install*.
. On the Install Operator page, configure the following:
+
[cols="1,2"]
|===
| Setting | Value

| Update channel
| `stable`

| Installation mode
| All namespaces on the cluster

| Installed Namespace
| `openshift-operators`

| Update approval
| Automatic
|===
+
. Click *Install*.
. Wait for the status to show *Succeeded*.

== Step 4: Create the S3 Storage Secret

LokiStack needs S3 credentials to store log data. Your S3 bucket has been pre-created. Use the credentials from the information panel on this page.

. In the OpenShift web console, select the *openshift-logging* project from the namespace dropdown at the top.
. Navigate to *Workloads > Secrets*.
. Click *Create* and select *Key/value secret*.
. Set the *Secret name* to `logging-loki-s3`.
. Add the following key/value pairs (click *Add key/value* to add each additional entry):
+
[cols="1,2",subs="+attributes"]
|===
| Key | Value

| `bucketnames`
| `{s3_bucket_name}`

| `region`
| `{s3_region}`

| `access_key_id`
| `{s3_access_key_id}`

| `access_key_secret`
| `{s3_secret_access_key}`

| `endpoint`
| `\https://s3.{s3_region}.amazonaws.com`
|===
+
. Click *Create*.
. Verify the secret appears in the Secrets list with the name `logging-loki-s3`.

== Step 5: Deploy LokiStack

. Navigate to *Operators > Installed Operators*.
. Select the *openshift-logging* project from the namespace dropdown.
. Click on *Loki Operator*.
. Click the *LokiStack* tab.
. Click *Create LokiStack*.
. Switch to the *YAML view* and replace the contents with the following:
+
[source,yaml]
----
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  size: 1x.extra-small
  storage:
    schemas:
      - version: v13
        effectiveDate: "2024-10-01"
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: gp3-csi
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 3
----
+
. Click *Create*.
. Wait for the LokiStack status to show *Ready*. This may take 3-5 minutes. You can monitor the status on the LokiStack details page or by navigating to *Workloads > Pods* in the *openshift-logging* namespace to watch the Loki pods start up.

== Step 6: Configure Log Collection

The ClusterLogForwarder tells the Logging Operator what logs to collect and where to send them. Before creating the forwarder, you need to create a service account with the required permissions.

[NOTE]
====
Open the *Terminal* tab and run these commands to create the required service account and grant log collection permissions:

[source,role="execute"]
----
oc create serviceaccount collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-application-logs -z collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-infrastructure-logs -z collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-audit-logs -z collector -n openshift-logging
----
====

Now create the ClusterLogForwarder using the console:

. Navigate to *Operators > Installed Operators*.
. Select the *openshift-logging* project from the namespace dropdown.
. Click on *Red Hat OpenShift Logging*.
. Click the *ClusterLogForwarder* tab.
. Click *Create ClusterLogForwarder*.
. Switch to the *YAML view* and replace the contents with the following:
+
[source,yaml]
----
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: collector
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
  pipelines:
    - name: application-logs
      inputRefs:
        - application
      outputRefs:
        - default-lokistack
    - name: infrastructure-logs
      inputRefs:
        - infrastructure
      outputRefs:
        - default-lokistack
    - name: audit-logs
      inputRefs:
        - audit
      outputRefs:
        - default-lokistack
----
+
. Click *Create*.
. Navigate to *Workloads > Pods* in the *openshift-logging* namespace. You should see collector pods running on each node. Wait for all collector pods to show a status of *Running*.

== Step 7: Enable Console Log Viewing

The Cluster Observability Operator provides a UIPlugin that adds a *Logs* tab to the OpenShift Console.

. Navigate to *Operators > Installed Operators*.
. Select the *openshift-operators* project from the namespace dropdown.
. Click on *Cluster Observability Operator*.
. Click the *UIPlugin* tab.
. Click *Create UIPlugin*.
. Switch to the *YAML view* and replace the contents with the following:
+
[source,yaml]
----
apiVersion: observability.openshift.io/v1alpha1
kind: UIPlugin
metadata:
  name: logging
spec:
  type: Logging
  logging:
    lokiStack:
      name: logging-loki
    logsLimit: 50
----
+
. Click *Create*.
. Verify the UIPlugin appears with the name `logging`. You may need to refresh the console page for the *Observe > Logs* menu item to appear.

== Step 8: Generate Test Logs

[NOTE]
====
Open the *Terminal* tab and run the following commands to generate test logs in your namespace:

[source,role="execute",subs="+attributes"]
----
oc run log-test-{seat_number} \
  --image=registry.access.redhat.com/ubi9/ubi-minimal:9.4 \
  -n student-{seat_number} \
  --restart=Never \
  -- /bin/bash -c 'for i in $(seq 1 10); do echo "{\"msg\":\"MAS World log test\",\"seat\":\"{seat_number}\",\"iteration\":$i,\"timestamp\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}"; sleep 2; done'
----

Wait about 25 seconds for the pod to finish generating logs, then verify the output:

[source,role="execute",subs="+attributes"]
----
oc logs log-test-{seat_number} -n student-{seat_number}
----

You should see 10 JSON log entries with your seat number.
====

== Step 9: Query Logs in the Console

Now use the integrated log viewer to find your test logs.

. In the OpenShift web console, navigate to *Observe > Logs*.
+
[TIP]
====
If you do not see the *Logs* menu item under *Observe*, try refreshing the browser page. The UIPlugin may take a moment to register.
====
+
. In the log query field, enter the following LogQL query to find your test logs:
+
[source,text,subs="+attributes"]
----
\{kubernetes_namespace_name="student-{seat_number}"} |= "MAS World log test"
----
+
. Click *Run Query* (or press Enter). You should see your 10 test log entries.
. Try a more specific query that filters by your seat number using JSON parsing:
+
[source,text,subs="+attributes"]
----
\{kubernetes_namespace_name="student-{seat_number}"} | json | seat="{seat_number}"
----
+
. Experiment with other queries:
+
* View all infrastructure logs: `\{log_type="infrastructure"}`
* View audit logs: `\{log_type="audit"}`
* Search across namespaces: `\{kubernetes_namespace_name=~"student-.*"} |= "MAS World"`

== Step 10: Clean Up

[NOTE]
====
Open the *Terminal* tab and run the following command to delete your test pod:

[source,role="execute",subs="+attributes"]
----
oc delete pod log-test-{seat_number} -n student-{seat_number}
----
====

After deleting the pod, navigate back to *Observe > Logs* and run your LogQL query again. Notice that the historical logs persist in Loki even after the pod is deleted -- this is a key benefit of centralized log storage.

== Production Considerations

[cols="1,1,2"]
|===
| Aspect | Workshop | Production

| Loki size
| `1x.extra-small`
| `1x.medium` or larger

| S3 storage
| Single bucket per cluster
| Dedicated bucket with lifecycle policies

| Retention
| 3 days (event duration)
| 30-90 days or longer per compliance

| SIEM integration
| Not configured
| Forward to Splunk, CloudWatch, or similar

| Log types
| Application + Infrastructure + Audit
| Same, plus custom forwarding rules

| Console integration
| COO UIPlugin (basic)
| Grafana dashboards + alerting rules
|===
